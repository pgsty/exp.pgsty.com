PG Exporter v1.5.0 updates the Go toolchain and dependencies, fixes replication collector identity and state mappings, and closes six runtime defects around target URLs, discovery, health, collector planning, durations, and HTTP routing.

The bundle still contains **58 YAML files, 96 collector branches, 59 namespaces, and 460 distinct metric definitions**. The metric count spans all version branches, including disabled collectors and two unexpanded SQL histograms; it is not a promise of 460 series in each scrape.

## Changes

- **Safer connection URLs:** malformed URL syntax, query escaping, or unsafe decoded parameter names stop startup without exposing the original connection string. Explicit TLS options can no longer disappear silently when malformed parameters are normalized. An empty or whitespace-only selected `PG_EXPORTER_URL_FILE` also fails startup.
- **Correct database discovery:** database identity follows `lib/pq`, including the `dbname` and `database` aliases. Discovery removes conflicting database parameters when substituting a database path and preserves special characters. This prevents repeated collection of one database, duplicate samples, and resulting HTTP 500 responses.
- **Consistent health responses:** each response derives its status code and body from one atomic state snapshot. Concurrent probes, scrapes, and reloads can no longer combine HTTP 200 with a `down` or `starting` body. Health still reports cached target state.
- **Collector plans follow metadata:** changes to the connected user, schema set, or extension set invalidate the plan after a successful metadata precheck. New eligible collectors appear on the next scrape; removed dependencies stop selecting collectors. Unchanged sets preserve their caches.
- **Bounded configuration durations:** YAML TTLs, timeouts, and predicate TTLs reject NaN, infinity, and positive duration overflow. Zero/default semantics and finite negative timeouts that disable deadlines remain unchanged.
- **Reachable metrics paths:** startup checks the actual metrics handler selected by the active HTTP mux, including decoded paths and redirects. A path cannot pass validation while routing to the homepage or a redirect.
- **Replication identity and states:** every `pg_sub_*` sample gains a `datname` label, distinguishing subscriptions with the same name in different databases. `pg_recv_state` uses the actual receiver states, and its legacy query uses PG9.6-compatible `substring()`.
- **More precise collector descriptions:** document optional replication-origin permissions, publication table counts versus subscription table/sequence counts, and `pg_backend` grouping by backend type. These description changes do not add metric families or enable optional collectors.

## Metric and dashboard compatibility {#metric-compatibility}

Compared with v1.4.1 on the same PostgreSQL version, **v1.5.0 does not add, remove, or rename bundled SQL metric names**. Types and units remain unchanged, but labels and state mappings do change. PostgreSQL 19 support first shipped in [v1.3.0](/release/v1.3.0/); upgrading the database can also change the selected SQL branch and a metric's meaning.

| Scope | Metrics | Compatibility action |
|:---|:---|:---|
| v1.5.0 configuration | `pg_sub_*` | Adds `datname` to every sample. Keep database and subscription identity in joins and aggregations; new label sets create new time series. |
| v1.5.0 configuration | `pg_recv_state` | Real receiver states `starting`, `waiting`, `restarting`, and `stopped` now map to 6–9 instead of `-1`. Update value mappings and state alerts; codes 1–3 are reserved. |
| PG18 → PG19 | Existing PG18 metric names | None are removed or renamed by the PG19 branches in this bundle. This does not guarantee unchanged semantics or labels from PostgreSQL itself. |
| PG19 | `pg_sub_sync_error_count` | Keeps the name but becomes the sum of table and sequence synchronization errors. For table-only alerts, use `pg_sub_sync_table_error_count`; `pg_sub_sync_seq_error_count` reports the sequence component. Do not double-count the components and their sum. |
| PG19 | `pg_sub_has_worker`, `pg_sub_reset_time`, `pg_sub_confl_*` | Adds worker presence, reset time, and eight conflict counters. The subscription row can remain without an apply worker; metric presence alone is not a worker-health check. |
| PG19 | `pg_subrel_count` | Includes sequences as well as tables; `pg_pubrel_count` still counts tables only. Review panel labels and count comparisons. |
| PG19 | `pg_wal_fpi_bytes`, `pg_lock_stat_*`, `pg_recovery_state_*`, `pg_vacuum_score_*` | Additive metrics. Recovery state is replica-only; autovacuum scores are primary-only. Existing WAL, lock-distribution, and recovery families remain. |
{.full-width .wide .expand}

Users upgrading from PG17 or earlier must also migrate older names: checkpoint metrics left `pg_bgwriter_*` in PG17, and `pg_wal_write`, `pg_wal_sync`, `pg_wal_write_time`, and `pg_wal_sync_time` are absent from PG18 onward. The [full compatibility guide](/compatibility/#older-postgresql-metrics) lists each replacement, label/aggregation differences, and mixed-version PromQL.

Before rollout, evaluate the actual dashboard and alert expressions and test missing-series input. A successful scrape does not ensure every expected metric exists; an empty alert expression can silently stop firing. The [missing-metric checks](/compatibility/#missing-metric-alerts) include a per-target rule and explain when absence is expected. The full [PG19 metric table](/compatibility/#postgresql-19-metrics) links to the tagged collector definitions; PostgreSQL validation remains scoped to 19 RC1.

On 2026-10-23, `govulncheck` found **no symbol-level or imported-package vulnerabilities** in the v1.5.0 candidate for Darwin/arm64, Linux/amd64, and Windows/amd64. ## Upgrade notes

1. **Deploy the matching collector configuration.** Upgrading only the binary does not apply SQL or label corrections. Compare local customizations before replacing `/etc/pg_exporter.yml`.
2. **Review the `pg_sub_*` label change.** The new `datname` label creates new time series. Keep database identity in PromQL joins and aggregations where needed. `pg_sub_id` remains a Gauge.
3. **Grant the PG10–13 subscription prerequisite.** As an administrator, run the following in each database used as the exporter's **main connection database**, using the actual monitoring role. Granting it only in a subscription's database is insufficient. It does not expose `subconninfo`; PG14+ needs no extra grant under standard catalog ACLs.

   ```sql
   GRANT SELECT (oid) ON pg_catalog.pg_subscription TO monitor;
   ```

4. **Check receiver-state alerts.** `streaming=0`, `stopping=4`, `connecting=5` (PG19+), `starting=6`, `waiting=7`, `restarting=8`, `stopped=9`, and unknown/NULL `=-1`; codes 1–3 are reserved. A missing receiver row remains absent.
5. **Correct previously tolerated invalid input.** Broken URL escapes, empty selected URL files, non-finite durations, and unreachable metrics paths now fail validation. Prefer `/metrics` for compatibility with both HTTP mux implementations.

Omitted `sslmode` still defaults to `disable`; configure TLS explicitly for remote connections. The scratch container still requires a mounted CA for certificate verification. Empty YAML reloads still apply zero configured collectors, invalid files in a directory may be skipped, and `SIGTERM` does not wait for active HTTP requests. See [Security](/security/), [HTTP API](/api/), and [Bundled Collectors](/collectors/) for the operating contracts.

## Validation scope

Pre-release validation covered the race suite, both HTTP mux modes, static analysis, module and generated-config consistency, roughly 604,000 short-run fuzz cases, and six target builds. Non-superuser default collection passed on PostgreSQL 9.1–9.6, 10–18, 19 RC1, and PgBouncer 1.26.1. Runtime checks included conflicting database aliases, special database names, schema/extension changes, failed reloads, reconnect recovery, physical standby promotion, and concurrent HTTP requests. RPM/DEB installation and Docker builds were also checked.

These checks cover the recorded versions and scenarios, not every extension combination or production workload. Composite, Patroni, pgBackRest, and PostgreSQL-log components remain development work outside v1.5.0.
